# Архитектура проекта

## Общая логика системы

Система работает как итеративный цикл.

```text
Производственный профиль
        ↓
Анализ возможностей
        ↓
Подбор заказов
        ↓
Рекомендации
        ↓
Уточнение производственного профиля
        ↺
```
Если подходящих заказов мало или они не найдены, система показывает, 
каких данных или производственных возможностей не хватает, и предлагает
уточнить профиль.

## Регистрационные и классификационные данные

### Источник, провайдер и граница системы

ЕГРЮЛ — государственный реестр и источник юридически значимых регистрационных
сведений о российском юридическом лице. Технический доступ в текущей
интеграции выполняется через внешний сервис `api-fns.ru`. Этот сервис является
провайдером данных ЕГРЮЛ, но не должен называться официальным API ФНС или
прямой интеграцией с инфраструктурой ФНС.

Каталог `backend/app/integrations/fns/` является внутренним интеграционным
слоем Production Navigator. Его назначение — изолировать контракт конкретного
внешнего сервиса, преобразовать ответ провайдера в нормализованное внутреннее
представление и передать его прикладному сценарию. Название каталога обозначает
предмет интеграции, а не доменную сущность и не гарантию прямого подключения к
ФНС. Провайдер должен оставаться заменяемым без изменения доменных моделей.

| Слой | Ответственность | Что в него не входит |
|------|-----------------|-----------------------|
| Инфраструктурный | HTTP-клиент `api-fns.ru`, endpoint, аутентификация, транспортные ошибки и провайдерский JSON | Правила заполнения профиля и доменные решения |
| Прикладной | Проверка входного ИНН, нормализация, сопоставление полей, подготовка предварительного заполнения и импорт после подтверждения | Провайдерские поля как часть публичного доменного контракта |
| Доменный | `EnterpriseProfile`, `EnterpriseOKVED`, локальный `OKVED`, отдельно — `Industry` и производственный профиль | `api-fns.ru` как сущность или источник производственных возможностей |

### Текущее состояние и целевой поток

Текущая реализация ограничена автономной функцией `req_fns(inn)` в
`backend/app/integrations/fns/client.py`. Endpoint не зашит в клиент и берётся
из `settings.url_fns`; ИНН передаётся query-параметром `req`, а ключ из
`settings.api_fns_key` — query-параметром `key`:

```text
ИНН
  ↓
HTTP GET к endpoint из конфигурации с ключом из окружения
  ↓
api-fns.ru
  ↓
raise_for_status()
  ↓
response.json() без нормализации
  ↓
сырой разобранный JSON вызывающему коду
```

Клиент не подключён к FastAPI router, не имеет схемы ответа, слоя
нормализации или сервиса импорта. Аннотация возвращаемого значения `int` не
соответствует фактическому возврату JSON. Содержащаяся в модуле ручная точка
запуска печатает результат и подтверждает автономный диагностический характер
клиента; это не прикладной endpoint и не целевой способ журналирования данных.

Целевой поток:

```text
ИНН пользователя
  ↓
прикладной сценарий поиска регистрационных сведений
  ↓
интерфейс провайдера → адаптер api-fns.ru → провайдерская схема ответа
  ↓
нормализованные регистрационные данные
  ↓
проверка кодов по локальному OKVED
  ↓
предварительное заполнение EnterpriseProfile + EnterpriseOKVED
  ↓
подтверждение пользователем
  ↓
сохранение
```

| Компонент | Сейчас | Целевое состояние |
|-----------|--------|-------------------|
| HTTP-клиент | Одна функция напрямую вызывает URL из `Settings` через `httpx.AsyncClient` | Реализация интерфейса заменяемого провайдера, изолированная в инфраструктурном слое |
| Разбор ответа | `response.json()` возвращается без проверки структуры; тип аннотирован неверно | Провайдерская схема валидирует внешний контракт, затем адаптер строит внутреннюю нормализованную модель |
| Нормализованная схема | Отсутствует | Провайдер-независимый объект регистрационных данных с явно согласованными обязательными и необязательными полями |
| Импорт `EnterpriseProfile` | Отсутствует | Прикладной сервис готовит предварительное заполнение и сохраняет подтверждённые пользователем реквизиты |
| Импорт `EnterpriseOKVED` | Отсутствует; автоматическое создание в интеграции не реализовано | Основной и дополнительные коды проверяются по локальному `OKVED` и сохраняются как связи после подтверждения |
| FastAPI endpoint | Отсутствует; клиент не включён в API router | Отдельный прикладной endpoint поиска/предварительного заполнения с внутренним контрактом ответа |
| Обработка ошибок | Есть только `raise_for_status()` для HTTP-статусов; прикладное различение ошибок отсутствует | Типизированные результаты для некорректного ИНН, отсутствия записи, недоступности, ошибок провайдера и невалидного ответа |
| Абстракция провайдера | Прикладной контракт отсутствует, используется конкретный формат ответа | Интерфейс позволяет заменить `api-fns.ru`, не меняя домен, API онбординга и правила импорта |

Текущий код подтверждает только входной параметр ИНН и факт возврата
произвольного JSON. Он не кодирует состав полей ответа, поэтому на основании
реализации нельзя утверждать стабильную доступность КПП, адреса, статуса, даты
регистрации, полного или краткого наименования и кодов ОКВЭД. Точный
провайдерский контракт и примеры обезличенных ответов должны быть зафиксированы
отдельной схемой до реализации импорта.

Из уже существующей внутренней модели непосредственными кандидатами на
предварительное заполнение являются `company_name`, `inn` и `ogrn`.
`region_code` может заполняться только после отдельного однозначного
сопоставления адресных данных с локальным `Region`. `website`,
`employees_count` и `company_size_code` не следует считать регистрационными
данными ЕГРЮЛ без отдельно утверждённого источника. Основной и дополнительные
коды деятельности относятся не к полям `EnterpriseProfile`, а к связям
`EnterpriseOKVED`.

`OKVED` хранит локальное представление официального классификатора, а
`EnterpriseOKVED` — коды, зарегистрированные у конкретного предприятия.
Получение регистрационных сведений через провайдера не является загрузкой или
обновлением самого локального классификатора. Внешние коды сначала должны быть
проверены по `OKVED`; при отсутствии кода нельзя создавать связь с несуществующим
внешним ключом.

### Граница автоматического заполнения

Интеграция может подготавливать только регистрационные реквизиты
`EnterpriseProfile` и основной/дополнительные связи `EnterpriseOKVED`. Она не
подтверждает и не заполняет автоматически:

- `Equipment`, `Technology`, `Material`, `Product` и `ProductionFacility`;
- `QualityCapability`, фактические сертификаты, производственные мощности и
  реальную номенклатуру;
- способность выполнить заказ или результат matching;
- `EnterpriseIndustry`, основную `Industry` либо отрасль заказа.

`Industry` описывает внутренний отраслевой или рыночный контекст PNC. Даже
основной ОКВЭД не является достаточным основанием для автоматического назначения
основной `Industry`; отдельное правило сопоставления пока не спроектировано.

### Конфигурация, секреты и ошибки

Endpoint внешнего сервиса задаётся конфигурацией, а API-ключ — переменной
окружения. Реальное значение ключа не должно храниться в Git, документации,
примерах, fixtures, логах, трассировках или тексте исключений. В документационных
примерах допустим только маркер `<API_KEY>`. Нельзя журналировать полный URL с
query-параметрами, если в них находится ключ, или сырой ответ с регистрационными
данными без отдельной политики безопасного логирования.

Целевой адаптер и прикладной сценарий должны различать следующие ситуации:

- синтаксически некорректный ИНН;
- таймаут и сетевую недоступность провайдера;
- ответы HTTP 4xx и 5xx;
- отсутствие записи для корректного ИНН;
- пустой или неполный ответ;
- отсутствие необязательных полей;
- изменение структуры внешнего JSON;
- некорректный код ОКВЭД в ответе;
- корректный внешний код, которого ещё нет в локальном `OKVED`.

Ошибки внешнего сервиса не должны приводить к частичной записи, молчаливому
обнулению существующих данных или подмене отсутствующих сведений догадками.
Провайдерские ответы и исключения не должны проходить в публичный API без
нормализации. Конкретные значения таймаутов, количество повторов, backoff,
circuit breaker, fallback и правила сохранения неразрешённых кодов пока не
утверждены и вынесены в backlog.

### Классификационный контекст

Локальный справочник `OKVED` используется для проверки кодов, поиска,
отображения названий и работы с иерархией без постоянной зависимости от
внешнего API.

Отдельно существует внутренний классификационный слой PNC:

```text
EnterpriseProfile ──< EnterpriseIndustry >── Industry
ProductionOrder  ──────────────────────────── Industry
```

`Industry` описывает отрасль или рынок применения в терминах Production Navigator. Для предприятия это обслуживаемый рыночный сегмент, для заказа — отрасль конечного применения. Основной `OKVED` не назначает основную `Industry` автоматически; однозначное сопоставление между этими классификациями не определено.

## 1. Производственный профиль

Назначение:
хранение структурированной информации о производственных возможностях
предприятия без сбора лишних персональных данных.
Производственный профиль состоит из двух типов данных:

- структурированные данные — выбираются из справочников и используются для автоматического анализа;
- описательные данные — свободный текст, примеры работ, особенности производства, которые могут использоваться для AI-анализа и формирования PDF-профиля.

Регистрационные `OKVED` и рыночные `Industry` входят в цифровой профиль предприятия как контекст, но не являются доказательством производственных возможностей. Фактические возможности описываются следующими разделами.

### Продукция
- что производится сейчас;
- серийная продукция или изделия под заказ;
- наличие каталога продукции;
- минимальная и максимальная партия;
- типовые сроки изготовления;
- примеры выполненных работ.
### Оборудование
- типы станков и оборудования;
- количество единиц оборудования;
- наличие ЧПУ;
- тип ЧПУ: 3-осевой, 4-осевой, 5-осевой;
- рабочая зона;
- максимальная масса детали;
- состояние оборудования;
- режим работы.
### Материалы
- сталь;
- нержавеющая сталь;
- алюминий;
- латунь;
- пластик;
- титановые сплавы;
- резина;
- композиты;
- другие материалы.

В дальнейшем материалы должны быть оформлены как двухуровневый 
справочник:

тип материала → марка материала
###Технологии

Технологии должны быть сгруппированы по категориям.

### Механическая обработка

## 2. Анализ возможностей

На основании производственного профиля система анализирует, какую продукцию предприятие может производить и какие ограничения необходимо учитывать.

Анализ включает:

- определение доступных производственных направлений;
- сопоставление технологий, материалов, размеров и оборудования;
- выявление ограничений;
- определение недостающих возможностей;
- оценку готовности к участию в закупках.

Анализ должен быть преимущественно детерминированным:

```text 
правила + справочники + структурированные данные
```

AI-модуль используется как дополнительный слой для анализа описаний,
нечетких совпадений и формирования рекомендаций.

### Карта производственных возможностей

Результатом анализа является карта производственных возможностей предприятия. Она связывает сведения профиля с требованиями рынка и разделяет заказы на следующие группы:

- доступны при текущих возможностях;
- доступны при устранении отдельных ограничений;
- недоступны из-за критического несоответствия;
- не могут быть оценены из-за недостатка данных.

Для каждого заказа система должна показывать, какие характеристики профиля повлияли на результат и какие действия могут изменить оценку.

### Виды ограничений

Обнаруженные несоответствия классифицируются следующим образом:

- **критическое ограничение** — заказ невозможно выполнить при текущих подтвержденных возможностях;
- **устранимое ограничение** — потребуется закупка материала, аренда, субподрядчик, получение документа или другое выполнимое действие;
- **недостаточно данных** — система не может достоверно оценить соответствие;
- **рекомендация** — улучшение не является обязательным, но может повысить конкурентоспособность предприятия.

Отсутствие материала, собственного склада или транспорта не должно автоматически считаться критическим ограничением: необходимый ресурс может быть приобретен, арендован или привлечен по договору.

## 3. Подбор заказов

Система подбирает заказы, которые соответствуют производственному
профилю предприятия.

`OKVED` не используется как самостоятельный критерий производственной совместимости: зарегистрированный вид деятельности не подтверждает наличие нужных ресурсов. `Industry` может задавать отраслевой контекст, compliance и специальные требования только там, где это определено отдельным бизнес-правилом. Основной matching опирается на подтверждённые характеристики продукции, материалов, технологий, оборудования, качества и инфраструктуры.

Подбор выполняется по следующим параметрам:

- продукция;
- материалы;
- технологии;
- размеры деталей;
- объемы;
- сроки исполнения;
- регион;
- наличие необходимых документов и сертификатов.
### Жесткие фильтры

Жесткие фильтры исключают заведомо неподходящие заказы:

- регион;
- тип закупки;
- начальная максимальная цена;
- срок исполнения;
- необходимые сертификаты;
- необходимые технологии;
- максимальные размеры и масса изделия.
### Мягкие фильтры

Мягкие фильтры влияют на ранжирование:

- степень соответствия производственному профилю;
- близость по технологиям;
- близость по материалам;
- уровень конкуренции;
- повторяемость похожих заказов.
## 4. Рекомендации

Система формирует рекомендации по наиболее перспективным
направлениям.

Рекомендации должны быть объяснимыми. Система должна показывать
не только подходящие заказы, но и причины подбора.

Рекомендации могут включать:

- топ подходящих заказов;
- объяснение, почему заказ подходит;
- список ограничений;
- недостающие документы или возможности;
- рекомендуемую продукцию;
- действия, которые нужно выполнить для участия в закупке;
- рекомендации по развитию производственных возможностей.

Рекомендации можно делить по срочности:

- сделать сейчас;
- подготовить в ближайшее время;
- запланировать на развитие.
## 5. Принципы проекта
- система собирает только данные, необходимые для анализа 
производственных возможностей;
- персональные данные физических лиц в MVP не собираются;
- данные юридического лица могут использоваться только при
необходимости и с согласия пользователя;
- сначала описываются возможности производства, затем 
подбираются заказы;
- рекомендации должны быть объяснимыми;
- пользователь должен иметь возможность экспортировать свои данные;
- система не заменяет технолога, а помогает руководителю принимать 
решения;
- полнота профиля характеризует достаточность данных для анализа, а не
уровень развития предприятия;
- выводы системы должны различать подтвержденный факт, экспертную
